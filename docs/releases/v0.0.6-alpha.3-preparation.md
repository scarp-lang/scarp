## Candidate integration

- [ ] Cargo version, lockfile and release metadata all match
  `0.0.6-alpha.3` in the final candidate source.
- [ ] Both versioned release notes and independently reviewed public-facing
  notes are present in the tagged source tree.
- [ ] Package and archive verifiers require every inherited alpha.2 feature
  plus the two new docs and both new executable example/output pairs.
- [ ] Tests reject missing or altered new release files, stale metadata,
  and candidate-only wording in public release notes.
- [ ] Native packaged interpreter runs all bundled examples and matches
  every `.stdout` file on all three platforms.
- [ ] Exact final candidate PR head passes all four Rust checks (Ubuntu,
  Windows, macOS and minimum Rust 1.74) and three package jobs.
- [ ] Candidate PR is reviewed and merged; fresh **main push** jobs all pass
  on the final candidate source SHA. Prior commit CI is only historical evidence.
- [ ] Maintainer separately reviews the proposed version, release scope,
  source SHA and publication window (if any). Do not create
  `.github/release-request.json` in the candidate PR.
- [ ] Release-control PR contains an expressly approved full source SHA,
  version, tagger name/email, and optional paired UTC window. That newer
  control revision independently passes its seven required CI checks.
- [ ] Publisher verifies exact-tag source, all three native archive payloads,
  checksum sidecars, combined `SHA256SUMS`, clean build records and public
  downloaded bytes. Prerelease must be true and not the latest stable release.
- [ ] Separate immutable post-publication validation record is created and
  the one-time request is retired.

A validated PR or this file does **not** authorize release. Do not add
guessed source hashes, asset checksums, GitHub Actions URLs or publication
dates. [Release engineering policy](../releasing.md) controls each step.
